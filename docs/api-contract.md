# LARIS API contract (v0, owner = lead; agents must not change it without saying so)

Base `/api`. JSON. Auth is simulated: header `X-Role: owner|staff` and `X-User: <uuid>`. Staff responses NEVER contain cost, margin, supplier cost, or owner_only attrs.
Money is a string with 2-4 decimals (e.g. "123.4000"). Dates ISO-8601. Statuses and directions are the enums in db/schema.sql.

## Types
Doc summary: {id, direction:"in"|"out", kind, doc_no, party:{id,name}, status, issued_on, valid_until, total, currency, updated_at, flags:{cost_is_stale:bool, needs_review:bool}}
Line: {id, line_no, item_key|null, description, qty|null, uom, unit_price|null, discount_pct|null, tax_rate|null, section|null, is_header, needs_review, ocr_confidence|null, attrs:{}, attrs_unmapped:{}, min_qty|null, supplier_sku|null, review_reason|null}   (the last three are owner only: null for staff; min_qty is the supplier price-tier break, >1 = a minimum order quantity)
Provenance (owner only): {line_id, cost_item_id, supplier, source_doc_id, source_doc_no, source_line_id, cost_date, unit_cost, cost_snapshot, current_unit_cost, cost_is_stale, line_margin}

## Endpoints
- GET  /api/me -> {role:"owner"|"staff" (the class), role_key, role_name, permissions:[key], id, name, org:{name, brand_color|null, logo_url|null}}   (org = tenant branding for every signed-in role: name = display name else the registered name, brand_color `#rrggbb`, logo_url = an inline `data:image/...` URL, else the `ORG_LOGO_URL` env, else null = initials placeholder; `permissions` drives nav and guards, see docs/roles.md)
- GET  /api/tracker -> {received:[DocSummary], sent:[DocSummary]}   (two lanes, shared states)
- GET  /api/documents/{id} -> {doc:DocSummary+terms, lines:[Line], provenance?:[Provenance] (owner), messages:[{direction,channel,body,at}]}
- POST /api/documents/{id}/transition {to:status, reason?} -> DocSummary   (owner for approve/accept/reject; 403 otherwise; 409 if transition not allowed)
- POST /api/documents/{id}/lines/{lineId} {item_key?, qty?, unit_price?, needs_review?} -> Line   (review step for 'in' docs; unit_price on 'out' lines is rules-engine only, 403)
- GET  /api/alerts/stale-costs (owner) -> [{quote_id, quote_no, customer, item_key, old_cost, current_cost, margin_delta, status}]
- GET  /api/cost-items (owner) -> [{id,item_key,uom,unit_cost,supplier,source_doc_no,effective_date}]
- GET  /api/fields -> [{key,label,type,unit,options,show_in_grid,sort_order}]  (staff: owner_only removed)
- GET  /api/field-proposals (owner) -> [{id,key,sample_values,status}] ; POST /api/field-proposals/{id}/decide {decision:"approve"|"ignore", type?, label?}
- GET  /api/audit?after=<id> -> [{id,at,actor,entity,entity_id,event}]   (poll cursor = last id; also used as the live-update feed). When staff change a supplier line's `unit_price` the event reads `review edit: unit_price (price 40.0000 -> 45.5000)` for the owner; staff see `review edit: unit_price` without the figures
- POST /api/enquiries/simulate {channel, text} -> creates a draft out quote via extraction+rules (demo helper). Limited to 30 requests per user per 10 minutes, shared with `POST /api/documents/ingest`: 429 `slow_down`
- POST /webhooks/telegram , GET+POST /webhooks/whatsapp (Meta verify + inbound; delivery/read status updates documents.read_at)
- GET  /api/export/bom.xlsx?quote_id= , /api/export/po.csv?quote_id=

Errors: {error:{code,message}}; list endpoints return [] when empty.

## Additions after v0 (all in the repo, all tested in `tests/test_api.py`)

Responses are scrubbed of cost and margin fields for anyone whose role lacks `view_costs` (staff by default) on every endpoint below. "Owner" means owner only. "Any" endpoints that need a permission answer 403 `permission_required` without it (`upload_documents`: ingest and manual; `manage_contacts`: contact create and edit; `edit_supplier_contacts`: a supplier's name or number, 403 `owner_only` kept for old clients; `ask_suppliers`: `POST /api/rfq`; `view_replies_prices`: prices and text in `GET /api/rfq`; `view_costs`: cost items, stale alerts, BOM/PO with `export_data`; `view_reports`: margin report; `manage_followups`: acting on a follow-up; `export_data`: contacts CSV; `view_audit`: the activity feed). The default staff role holds `manage_contacts`, `upload_documents`, `ask_suppliers` and `view_audit`, which is exactly what staff could do before roles existed.

| Endpoint | Who | What |
|---|---|---|
| `GET /api/auth/config`, `POST /api/login`, `POST /api/logout` | public / any | Accounts. Login returns a session token (stored server side only as SHA-256, expires after `SESSION_HOURS`, default 12). Wrong user and wrong password give the same error. 5 failed tries lock a username for 1 minute, doubling to 15 minutes; 30 failed tries per client address per 15 minutes across usernames; both give 429 (`too_many_attempts`) |
| `POST /api/signup` | public | Register a business: `{business_name, owner_name, email, password, trade_template}` (names 2-80 characters, plain text, control characters stripped; email up to 254; `trade_template` = a file key in `config/templates`, 422 `unknown_template` otherwise; password rules as below, the user name for the weak check is the email's part before `@`). Creates the tenant (with the template's fields and the owner/staff roles) and an inactive owner, and emails a 6-digit code. **Always** `202 {ok:true, message:"If this email can be used, we sent a 6-digit code"}`, whether or not the email is already registered (a registered email gets a short "you already have an account" mail instead; an unverified earlier attempt is replaced). 429 `slow_down`: 5 per client address and 3 per email per hour. With `SIGNUP_DEV_ECHO=1` and email off the answer also carries `dev_code` (demo only) |
| `POST /api/signup/verify` | public | `{email, code}` -> `200 {ok:true}`: the owner becomes active (no sign-in is issued; the UI sends the person to the login screen). Code: 6 digits, 10 minutes, 5 wrong tries then dead. Every failure is `400 invalid_code` "invalid or expired code" (unknown email, wrong, expired, used, dead) |
| `POST /api/signup/resend` | public | `{email}` -> `202` as signup. Only an unverified signup gets a new code (the old one dies). 429: 3 per email and 10 per client address per 15 minutes |
| `POST /api/password/forgot` | public | `{email}` -> `202` as signup, whether or not the account exists. Only verified, active accounts get a code. 429: 3 per email and 10 per client address per 15 minutes |
| `POST /api/password/reset` | public | `{email, code, new_password}` -> `200 {ok:true}`. Same code rules and the same uniform `400 invalid_code`; 422 `weak_password` (checked before the code is spent). Signs the person out everywhere (API token and all sessions) and clears the sign-in lock for them |
| `POST /api/login` also accepts a verified email address as `username` | public | An unverified signup gets the same 401 `bad_credentials` as a wrong password |
| `POST /api/me/password` | any | Change own password (10+ characters, not a very common password, not the username: 422 `weak_password`); other devices and the API token are signed out. Wrong `current` is throttled per user (429) |
| `GET /api/me/sessions` | any | Own live sessions: `id`, `created_at`, `last_seen_at` (updated at most once a minute, may be null), `user_agent`, `current` |
| `POST /api/me/sessions/revoke-others` | any | Sign out every other device; returns `{"revoked": n}` |
| `DELETE /api/me/sessions/{id}` | any | Sign out one of your own sessions; 404 for anyone else's (also across tenants) |
| `GET/POST /api/users`, `POST /api/users/{id}` | owner | Add people, set password, change role, deactivate. A role is named by `role_id` (uuid) or `role` (a role key such as `owner`, `staff`, `senior-buyer`): exactly one on create, and on edit when changing it (422 `role_needed` / `unknown_role`). Rows carry `role` (class owner\|staff), `role_id`, `role_key`, `role_name`. Changing role, password or active signs the person out everywhere. The last active owner cannot be removed or given a staff-class role (the tenant's owner rows are locked first, so two simultaneous demotions cannot leave none) |
| `GET /api/roles` | owner | `{roles:[{id, key, name, class, is_system, permissions:[key], users}], catalog:[{key, label, description, group, default}], non_assignable:[{key, label}]}`. The owner role lists every permission |
| `POST /api/roles` | owner | `{name, permissions:[key]}` -> 201 role. Always class staff; `key` is a slug of the name. Owner-only keys -> 422 `not_assignable`, unknown keys -> 422 `unknown_permission`, same name -> 409 `name_taken` |
| `PATCH /api/roles/{id}` | owner | `{name?, permissions?}`. The owner role and system role names are immutable (409 `system_role`); the system staff role's permissions are editable. Takes effect on the next request of everyone holding it |
| `DELETE /api/roles/{id}` | owner | Custom roles only; 409 `role_in_use` while anyone holds it, 409 `system_role` for owner and staff, 404 for another tenant's role |
| `GET/POST /api/contacts`, `GET/POST /api/contacts/{id}` | any | Contact book (customer, supplier, contractor). `GET` takes `q` and `role`. Owner also gets `value` and, for a supplier, `current_costs`. Staff may not change a supplier's `name` or `contact` (403 `owner_only`); every `contact` change is audited with the old and new value |
| `GET /api/search?q=` | any | Contacts, documents (number, party, line text); owner also cost items |
| `POST /api/assistant`, `GET /api/assistant/suggestions` | any | Look-up chat. The model picks an intent from a closed list; the answer is built from the database; it never changes data. Without the model it falls back to keywords (`source: "keywords"`) |
| `GET /api/dashboard` | any | Home numbers |
| `GET /api/jobs`, `POST /api/jobs/{id}` | any | Job board |
| `GET /api/followups`, `POST /api/followups/{id}` | list any, act owner | Suggested chase messages; `{"action": "send" \| "skip"}` |
| `GET /api/reports/margin?days=N` | owner | Margin report |
| `GET/POST /api/settings` | owner | Margin floor, issuer details for the quote PDF and branding: `display_name` (shown name, max 120; the registered `tenants.name` is not editable and the PDF issuer line uses the display name), `brand_color` (`#rrggbb`, stored lowercase), `logo_data_url` (`data:image/png\|jpeg\|webp;base64,...`, at most 200 KB decoded; the real bytes are sniffed and the data URL rebuilt, SVG or anything else -> 415 `unsupported_media`, too big -> 413 `too_large`). `null` clears a branding field back to its fallback. The audit log records `[image]`, never the bytes. Everyone signed in reads the result in `GET /api/me` |
| `POST /api/documents/manual` | any | Key in a supplier document by hand |
| `POST /api/documents/ingest` | any | Supplier document (multipart `file`, 10 MB, or form `text`; optional `supplier`, `kind`). The type is sniffed from the bytes, not trusted from the client: PDF (text layer), JPEG/PNG/WebP photo, XLSX (all sheets, first 2000 rows and 40 columns), DOCX (paragraphs and tables) or CSV (comma, semicolon or tab; UTF-8, GB18030 or Windows-1252; recognised by a `.csv` name or a `text/csv` type). Sheets and Word files are read as exact text, so there is no OCR confidence. Old `.xls`/`.doc` -> 415; a corrupt file, a Word file with a DOCTYPE/ENTITY, or a zip over 50 MB unpacked -> 422. Same extraction, validation, duplicate check (sha256 of the bytes) and review as a PDF. The same types work when sent as a document on WhatsApp or Telegram |
| `GET /api/documents/{id}/pdf` | any | Customer quotation PDF (selling prices only) |
| `POST /api/parties/{id}/erase` | owner | Erase a customer's personal data on request |
| `POST /api/rfq` | any | Ask suppliers (10 per user per 10 minutes, then 429 `slow_down`) (multipart): `image` (JPEG or PNG, 8 MB), `description` (200), `note` (300, optional), `circle` (optional JSON `{x,y,r}`, fractions), `supplier_ids` (repeated; each a supplier of this tenant with a phone or a `tg:<chat id>` contact, else 422). A supplier whose `contact` is `tg:<chat id>` or `telegram:<chat id>` (digits, may be negative for a group) gets the photo and note from the Telegram bot (`sendPhoto`); anyone else gets it on WhatsApp, once-uploaded, from the tenant's WhatsApp number (outside the 24h window it uses `WHATSAPP_RFQ_TEMPLATE`, else that send fails). A Telegram supplier who never pressed Start on the bot fails with `supplier must open the bot and press Start first`. Their replies come in through `/webhooks/telegram` (reply to our photo, or the newest open ask) and are acknowledged on Telegram. `rfq_sends.wamid` holds the provider message id for either channel (Telegram: `chat_id:message_id`). A failed send does not stop the others. -> `201 {rfq_id, sends:[{supplier_id, status:"sent"\|"failed", error}]}` |
| `GET /api/rfq` | any | Newest 100 asks: `[{id, description, note, created_at, image_url, replies:[{reply_id, send_id, supplier_id, supplier_name, text, unit_price, min_qty, tiers:[{min_qty, unit_price}], status}]}]`, one reply row per supplier asked (`waiting` until they answer). Staff get `text ""`, prices null, `tiers []`, and `status` only `waiting` or `needs_review` (answered). Owner status: `waiting`, `needs_review`, `ready`, `accepted` |
| `GET /api/rfq/{id}/image` | any | The photo (own tenant only) |
| `POST /api/rfq/{id}/replies/{reply_id}/accept` | owner | `{item_key}` (`^[a-z][a-z0-9_]{0,60}$`, else 422). Makes an inbound quotation from the reply (one line per price break, uom `pcs`), runs it reviewed -> accepted -> in_cost_book so cost items exist, sets the reply `accepted`. 409 if the reply has no price or is already accepted. -> `{reply_id, status, doc_id}` |
| `POST /api/listings` | staff, owner (`upload_documents`) | Catalog photo (multipart): `image` (JPEG, PNG or WebP, 8 MB), `supplier_id` (optional, a supplier of this tenant, else 422), `note` (300, optional). 10 per user per 10 minutes, then 429 `slow_down`. A vision model finds each product; the server validates it (max 60 items, bbox clamped, price > 0 or null), nulls any `sku` or `price` that OCR did not also read (reasons `unverified_sku`, `unverified_price`; `no_ocr_check` when OCR is unavailable), and stores one JPEG crop (6% padding, long side 600 px) per product. Every item starts `needs_review`. 503 `vision_not_configured` names the env vars to set (`RUNPOD_VISION_URL`, `RUNPOD_API_KEY`); 502 `vision_unavailable` when the model failed twice. -> `201 {listing_id, item_count, items:[item]}` |
| `GET /api/listings` | any | Newest 50: `[{id, party_id, party_name, note, source_channel, created_at, items, to_review, image_url}]` |
| `GET /api/listings/{id}` | any | `{id, party_id, party_name, note, source_channel, created_at, image_url, items:[{id, position, description, labels:[text as printed], sku, sizes, price, currency, bbox:[x0,y0,x1,y1] (0..1 of the photo), status:"needs_review"\|"confirmed"\|"discarded", reasons, item_key, crop_url}]}`. `price` and `currency` are null without `view_costs`. 404 for another tenant's listing |
| `GET /api/listings/{id}/image`, `GET /api/listings/{id}/items/{item_id}/crop` | any | The photo / the product's cropped JPEG (own tenant only) |
| `PATCH /api/listings/{id}/items/{item_id}` | staff, owner | Any of `description` (300), `sku` (80, null clears), `sizes` (max 30), `price` (> 0, needs `view_costs`, else 403), `status` (`confirmed` or `discarded`), `item_key` (`^[a-z][a-z0-9_]{0,60}$`). Audited with before and after. -> the item |
| `POST /api/listings/{id}/items/{item_id}/ask` | `ask_suppliers` | `{supplier_ids, description?, note?}`: the same as `POST /api/rfq` with this product's crop as the photo (same limits, sends and response `{rfq_id, sends}`). Description defaults to the product's description |

Chat: a WhatsApp or Telegram photo whose caption starts with `/catalog` or `catalog`, from a staff handle or a known supplier, creates a listing (reply: how many products are queued) instead of going to document ingest. Any other photo is unchanged.

Supplier replies reach `POST /webhooks/whatsapp`. A text from a supplier is linked to the ask it quotes (`context.id` = our message id), else to that supplier's newest ask still waiting (7 days). The price is read by ILMU from the redacted text; the server decides the status: `ready` only for a positive price (and sane breaks: dearer never at higher volume, ringgit), otherwise `needs_review`; the raw text is always kept. Voice notes and photos are stored `needs_review` (not read); a photo counts only when it quotes our message.

Identity, strongest first: a session or per-user token (`Authorization: Bearer`) decides user, role and tenant from the database and ignores `X-Role` and `X-User`; the shared `APP_TOKEN` or no token, both demo mode only. Demo mode (identity from `X-Role` / `X-User`) is allowed only while no account has a password, `REQUIRE_USER_TOKEN` is not `1`, and `DEMO_MODE=1` or (no `APP_TOKEN` and not a Replit deployment); otherwise 401 `bad_token`. With `APP_TOKEN`, `X-User` must be a user of the first tenant. `GET /api/auth/config` returns `login_required: true` exactly when demo mode is not allowed.
