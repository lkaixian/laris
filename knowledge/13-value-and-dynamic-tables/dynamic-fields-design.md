# Dynamic fields: new trade, new column ("finishing", "lead time", "per pax")

Short answer: yes, a new quotation can surface an unfamiliar field and the dashboard can gain a column, but only as AI proposes, owner approves, registry row appears. Nothing creates a Postgres column. Context: [[../07-data-model/bidirectional-schema]] ("Templates are config, not schema"), [[quote-value-insights]], [[dashboard-live-update]].

## Options compared (Postgres)
| Design | Add a field | Query | Types | Verdict |
|---|---|---|---|---|
| Fixed core + `attrs jsonb` per line + per-trade template schema | write a key, no DDL | `attrs->>'k'`, cast; GIN for containment; expression index for hot keys | app-enforced | **Recommended** |
| EAV (line_id, field, value) | insert row | pivots need self-joins or crosstab | weak | Reject (opinion: jsonb gives the same flexibility with simpler queries) |
| Per-trade generated tables / runtime ALTER TABLE | DDL per tenant | fastest, best typed | strong | Reject: migrations, locks, and AI-triggered DDL is unsafe |
| Schema-on-read views | regenerate view | readable | cast in view | Use for the dashboard, generated by app code from the registry, never by AI |
| Generated columns / materialised views | needs DDL once | indexable | typed | Later hardening: promote a hot, owner-confirmed field to `GENERATED ALWAYS AS ((attrs->>'lead_time_days')::int) STORED` via a human-run migration |

Postgres docs (retrieved 2026-10-22): prefer `jsonb`; "it is still recommended that JSON documents have a somewhat fixed structure"; `jsonb_path_ops` GIN is smaller but has no key-exists `?` operator, `jsonb_ops` has it; any update locks the whole row so keep documents small; the docs endorse mixing relational columns and JSON.

## Existing tools (high level)
- Baserow (verified): users add typed fields any time (text, number, date, single/multi select, link, lookup, rollup, formula...). Type conversion can lose data (text to number drops non-numeric). Docs suggest under 200 fields per table.
- Airtable / Notion (general knowledge): typed property per column, user-defined, change-type with warnings.
- Bukku / Zoho Books (general knowledge, unverified today): admin-defined typed custom fields on documents. See [[../05-competitors/bukku]], [[../05-competitors/zoho-books]].
- Lesson: in every one of them a human defines the field. We copy that rule.

## Recommended design (opinion)
### Layers
1. Fixed core columns on `document_lines` (description, item_key, qty, uom, unit_price): anything the pricing engine multiplies or the cost book keys on. Never JSONB. Per pax = `uom='pax'` in core.
2. `attrs jsonb`: trade-specific facts (finishing, lead_time_days, moq, break_qty).
3. `tenant_fields`: registry of approved keys (type, label, unit, applies_to, show_in_grid, owner_only). Drives UI columns and extraction schema.
4. `field_proposals`: unknown keys awaiting owner decision.
5. Template YAML seeds `tenant_fields` at tenant creation; afterwards the DB is the source of truth.

### One YAML, two consumers
```yaml
# config/templates/made_to_order.yaml (new `fields:` block beside item_catalog)
fields:
  - {key: finishing,      label: Finishing,        type: select, options: [raw, sanded, painted], applies_to: [in, out]}
  - {key: lead_time_days, label: Lead time (days), type: integer, unit: days, applies_to: [in]}
```
Registry rows become (a) the JSON Schema given to the LLM structured-output call (`attrs.properties.<key>` typed/enum, plus a separate `unknown_fields: [{key, value, evidence}]` array; vLLM supports JSON-schema structured outputs, see [[../06-tech-stack/adr-qwen3-vllm-runpod]]) and (b) the grid column list (label, type to renderer, unit suffix).

### Safe rule for "unknown field seen"
1. The LLM writes only to `attrs` keys in the schema it was given, plus `unknown_fields`. No DDL grant, no write on `tenant_fields` (same pattern as the no-price rule).
2. Unknowns go to `field_proposals(status='pending')` with sample values; the raw value is kept in `document_lines.attrs_unmapped` so nothing is lost but nothing shows in the grid.
3. Owner sees "New field seen: 'finishing' (3 docs). Add as column? [type] [Add] [Ignore]". Add inserts the `tenant_fields` row and back-fills `attrs` from `attrs_unmapped`. Ignore is remembered.
4. Never silently create columns. No ALTER TABLE in any app code path; the grid column exists because a registry row exists.
5. Key must match `^[a-z][a-z0-9_]{0,40}$`; keys are used only as JSON keys or bound parameters, never concatenated into DDL.
6. Values are type-validated on write; failures stay in `attrs_unmapped` and flag `needs_review`.
7. Every proposal decision goes to `audit_log`.

### DDL sketch (proposal only)
```sql
CREATE TYPE field_type AS ENUM ('text','number','integer','date','select','boolean');

ALTER TABLE document_lines
  ADD COLUMN attrs jsonb NOT NULL DEFAULT '{}',
  ADD COLUMN attrs_unmapped jsonb NOT NULL DEFAULT '{}',
  ADD CONSTRAINT attrs_are_objects CHECK (jsonb_typeof(attrs)='object' AND jsonb_typeof(attrs_unmapped)='object');
CREATE INDEX document_lines_attrs_gin ON document_lines USING GIN (attrs jsonb_path_ops);

CREATE TABLE tenant_fields (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id uuid NOT NULL REFERENCES tenants,
  key text NOT NULL CHECK (key ~ '^[a-z][a-z0-9_]{0,40}$'),
  label text NOT NULL,
  type field_type NOT NULL,
  unit text,
  options jsonb,
  applies_to doc_direction[] NOT NULL DEFAULT '{in,out}',
  show_in_grid boolean NOT NULL DEFAULT true,
  owner_only boolean NOT NULL DEFAULT false,   -- hidden from laris_staff views
  sort_order int NOT NULL DEFAULT 100,
  approved_by uuid REFERENCES users,
  created_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (tenant_id, key)
);

CREATE TABLE field_proposals (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id uuid NOT NULL REFERENCES tenants,
  key text NOT NULL,
  sample_values jsonb NOT NULL,
  source_line_id uuid REFERENCES document_lines,
  status text NOT NULL DEFAULT 'pending' CHECK (status IN ('pending','approved','ignored')),
  decided_by uuid REFERENCES users,
  decided_at timestamptz,
  UNIQUE (tenant_id, key)
);
```
LLM service role: INSERT on `field_proposals` only.

### Dashboard read path
Hackathon: the API returns lines (with `attrs`) plus the tenant's `tenant_fields`; the front end renders fixed columns then one column per registry row. Typed aggregate:
```sql
SELECT avg((attrs->>'lead_time_days')::int) FROM document_lines WHERE attrs ? 'lead_time_days';
```
Note `?` is not supported by a `jsonb_path_ops` index; use `jsonb_ops` if key-exists filters matter. Long-form view for BI-style use:
```sql
CREATE VIEW v_line_attrs AS
SELECT l.id AS line_id, l.document_id, d.tenant_id, kv.key, kv.value
FROM document_lines l JOIN documents d ON d.id=l.document_id
CROSS JOIN LATERAL jsonb_each_text(l.attrs) kv;
```
Casting `value` can fail on bad data, which is why write-time validation matters.

### Edge cases
- New trade: new template YAML seeds a new registry and item_catalog; no schema change.
- Remove a field: set `show_in_grid=false`; never strip keys from existing attrs.
- Promote to real column: human-run migration, never automatic.
